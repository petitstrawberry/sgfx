# SGFX 1.0 execution contract

Status: the architecture and coordinated Rust implementation policy in sections
1 and 2 were approved on 2026-09-06. Portable completion, safe rejection and
actual asynchronous Scarlet GPU submission are also agreed; see the
[completion contract](completion-contract.md). The other rendering, imported-image
and presentation clauses remain review targets. Approval of the architecture
does not certify their implementation or authorize a release.

The [Rust integration inventory](1.0-api-scope.md) describes today's exports
and the [execution notes](execution-contract.md) describe backend behavior.
The 1.0 boundary is an execution contract implemented by a matched source set;
it is not a blanket 1.x freeze of SGFX's Rust signatures.

## 1. Scope: a drawing/transfer IR with complete backends

Define the current resource, pipeline, upload, copy, and draw subset. SGFX
is a driver-facing execution IR, not an application API that must first grow
Vulkan-style device enumeration, arbitrary shaders, compute, or WSI. Those
extensions are not 1.0 prerequisites. This preserves the direction of
[issue #1](https://github.com/petitstrawberry/sgfx/issues/1) without claiming
that its entire future feature set is implemented.

Frontends describe logical work. Backends own device-specific validation,
physical resources, lowering, batching, transport limits, and submission.
Supporting another GPU must not require a second target-specific frontend IR.
Codegen helpers are building blocks, not executors or synchronization APIs.
The [architecture](architecture.md) maps these responsibilities to current code
and separates them from the Rust compatibility decision below.

The intended application-facing graphics boundary is the Vulkan C ABI.
`vulkan-sgfx`, `sgfx-core`, the selected backend and needed codegen can be linked
into one ICD/library. SGFX has no planned independently loaded Rust backend ABI.
ScarletUI can also link the SGFX implementation directly as a renderer, or use
a future Vulkan renderer. Adding a GPU backend should preserve these frontend
paths by implementing the common execution semantics.

## 2. Coordinated Rust implementation policy

SGFX's Rust exports are integration interfaces for components that are updated
and rebuilt together. This applies to `sgfx-core`, the `sgfx` facade,
`sgfx-backend-wgpu`, `sgfx-backend-scarlet-virgl`, `sgfx-codegen-virgl`, and the
external Adreno backend/codegen participating in the same driver build. It
includes the older direct VirGL/composition APIs and dependency types exposed
through the facade. Their `pub` visibility enables cross-crate composition;
these interfaces have no blanket source-compatibility guarantee throughout 1.x.

Direct Rust consumers must use a compatible revision/lockfile set and migrate
with an internal API change. This policy supersedes the previous proposal to
freeze all Rust exports and require an open/closed enum migration before RC1.
It does not remove existing exports or require an API rewrite now.

| Integration surface | Change rule |
| --- | --- |
| Enums and variant payloads | Evolve with their producers, match sites and lowerings in the same source set. There is no blanket `#[non_exhaustive]` requirement or permanently closed enum list. Existing annotations can remain where useful. Unsupported execution semantics must still produce an explicit error. |
| Traits, structs and descriptors | Required methods, bounds, fields and constructors can change with all affected implementations and consumers. Update their documentation and contract coverage together. |
| IR meaning and resource identity | Keep a single documented interpretation across frontends and backends. A representation change must preserve that interpretation or explicitly revise the supported subset and its consumers. It must not silently reinterpret existing commands. |
| Limits and feature recipes | Record the selected configuration, bounds and rejection behavior for each release. Update affected manifests and consumers together when changing them. Finite admission and safe failure remain required. |
| Exposed WGPU, window-handle and native Rust types | Update the backend/facade and their users together. They do not pin an application-facing Vulkan ABI or require freezing the current dependency types for all SGFX 1.x releases. |
| Distribution | Package versions identify component releases; candidate revisions and locks identify a compatible build. Require one `sgfx-core` source identity per binary. Independently replacing a Rust component in an existing binary is unsupported. |

Within a selected source set, backends must satisfy the same ownership,
ordering, completion and failure rules. Coordinated source updates do not
waive those execution obligations. A Vulkan frontend must preserve its external
Vulkan contract while adapting to internal changes. Scarlet's syscall/GPU ABI,
SWS wire protocol and ScarletUI's application-facing API retain their separately
defined compatibility policies.

## 3. Logical resources and recording

A resource ID identifies one immutable definition in one originating table.
Moving the table preserves identity; equal descriptors or indices in another
table do not. Definitions are append-only and dropping an ID does not delete
one. The table is not a concurrent recorder. GPU allocation and caching belong
to the backend, not to descriptor creation.

An imported texture's logical ID is distinct from its physical image binding.
After successful explicit release, the same definition may be bound to another
compatible image in that session. Its descriptor and table identity do not
change. A recorded command buffer stores logical references, not a snapshot
of physical bindings: replay resolves the session's current mappings.

Recording is fallible but locally atomic: a rejected operation appends no
command and leaves previously accepted bindings intact. An open pass reserves
its end command; abandoning it makes `finish()` fail. Core validates logical
usage, identity, bounds and required bindings. It does not scan uploaded index
values or certify device-specific support.

Command buffers borrow the table and upload data. On every return from
`execute`, including `Err`, the backend must no longer depend on borrowed
upload pointers. Accepted GPU work owns or retains everything it still needs.
Once Rust borrows end, the caller may reuse upload storage without waiting for
the GPU. This does not release an imported producer's content lease.

## 4. Rendering meaning, not backend-dependent approximations

These conventions apply to the portable IR. They do not silently redefine the
separate direct VirGL API.

- Transforms multiply column vectors using column-major 4x4 matrices. Position
  attributes with two or three components expand to `(x, y, 0, 1)` or
  `(x, y, z, 1)` respectively. Four-component positions retain their `w`.
- Clip space uses `-w <= x,y <= w` and `0 <= z <= w`. After division, NDC is
  x/y in `[-1, 1]` and depth in `[0, 1]`. Positive NDC y points up. Front-face
  winding is measured in NDC, before conversion to top-left pixel coordinates.
  Backends adapt their native conventions; frontends do not change matrices
  when switching GPUs.
- Pixel coordinates start at the top left, x right and y down. Rectangles are
  half-open. The viewport covers the full attachment; a pass's render area
  clips rendering and limits clears, rather than rescaling the viewport.
  Scissor is contained in that area; `None` restores the full render area.
- `Load` preserves previous contents, `Clear` initializes the render area,
  and `Store` preserves the result. With `Store`, defined contents outside a
  partial render area's clear/draw operations stay unchanged. `DontCare`
  permits discarding attachment contents; callers must not inspect or depend
  on discarded or otherwise uninitialized values.
- Depth is not a color format. A depth-enabled pipeline requires a matching
  attachment; a pipeline with depth disabled may use a pass that has one.
  Depth comparison/write semantics are explicit. A backend unable to handle
  an optional-depth combination or partial depth clear must reject it.
- Fragment programs, sample modes, and blend descriptors retain their stated
  component arithmetic. `R8Unorm` alpha-mask sampling uses red as coverage;
  RGBA/BGRA alpha masks use alpha. There is no implicit gamma conversion or
  premultiplication in these unorm formats. The chosen blend state and any
  platform presentation conversion remain explicit, separate concerns.

Different rasterizers may differ in precision, edge coverage, and rounding;
1.0 does not promise pixel-identical output. Such variation does not permit a
backend to ignore transforms, depth, blend state, clipping, or channel order.

## 5. Execution: separate acceptance and observable completion

`execute()` returning `Ok(())` means the complete logical stream was accepted
in recorded order. Sequential successful executions bound to the same queue
preserve resource access ordering. It does not mean GPU completion, CPU
visibility, cross-queue visibility, or presentation. An empty stream is a
no-op, not a wait.

The approved 1.0 scope now includes an owned submission receipt, nonblocking
completion observation and deadline-aware waiting, plus actual asynchronous
Scarlet GPU submission. The [completion contract](completion-contract.md)
specifies bounded acceptance, partial-failure receipts and lifetime rules.
Keep `execute` and existing synchronous GPU ABI operations compatible while
adding this path. Cross-queue GPU semaphores and presentation acknowledgements
remain distinct and are not supplied by a CPU completion wait.

## 6. Support and failure: explicit, non-transactional, conservative

Retain backend-specific errors and the existing coarse capability queries in
1.0. Do not add a mandatory common per-format capability or retry-classification
API. Capabilities describe availability, not support for every legal descriptor
or every combination. Each released backend must document its supported
operations and limits; an unsupported valid stream returns an explicit error.
An unsupported feature must not escape as an avoidable raw-driver validation
failure or silently change the rendering result.

Execution is not transactional. An error may follow uploads, passes, or
submitted chunks; acceptance may precede an asynchronous GPU/device fault.
Neither `Err` nor an unobserved asynchronous fault proves that no work ran.
Do not replay the stream or switch backends on the assumption of rollback.
Only a documented backend-specific recovery boundary can authorize reuse of
that state. Without one, abandon the affected session and rebuild resources;
do not free externally shared storage until its consumers are quiescent.

There is no common device-loss recovery guarantee in 1.0. Dropping/recreating
Rust objects alone does not prove a failed device stopped accessing memory.
Backends must retain safe ownership and expose faults through their documented
error/observation paths; `Ok` is never a substitute for observing completion.

## 7. Imported images: ownership is separate from permission to reuse

An import that takes a `Handle` by value takes ownership of that reference,
including when the call fails. On success, the backend retains an owner for
the mapping and in-flight uses. The caller does not need to retain the moved
Rust handle merely to avoid a dangling image. Producer permissions and frame
leases are separate: owning a reference does not authorize writing pixels
while another consumer may still read them.

Successful explicit `release_imported_texture` is a **session-local retirement
barrier**: the mapping is detached, and no previously accepted work in that
session can still access the old physical image. A backend must complete or
drain those uses before returning `Ok`; an asynchronous implementation cannot
weaken this guarantee. Releasing an already unmapped ID returns `ImageNotMapped`.
This retires that binding, not other aliases or future submissions. Other
sessions, queues, and external consumers are outside this guarantee.

A release error provides no reuse permission and no rollback guarantee.
Different backends may have detached different portions of their mapping state.
Do not rebind the ID, recycle the producer buffer, or send a release event on
that basis. Retain the producer lease until platform-specific quiescence is
established, or retire that buffer permanently. Use documented recovery or
rebuild the session; do not infer safety from retrying a failed release.

`Drop` must perform memory-safe cleanup but is not an observable completion
barrier or an SWS acknowledgement. A compositor can retain an SGFX mapping
across many commits: an SWS buffer-release event requires retirement of the
exact generation/epoch/serial and completion of all relevant consumer uses,
not necessarily SGFX unmapping on every frame. Neither successful `execute()`
nor one session's explicit release alone authorizes an SWS release or global
reuse.

## 8. Presentation, resize, and observation

Presentation is outside the command IR. Host `present()` success means the
surface frame was queued and handed to the presentation system, not that a
monitor displayed it. The target must belong to the same compatible device
and logical session; mismatches must be reported before raw-driver use.
Transparent presentation must preserve alpha, with an explicit conversion
when the surface requires premultiplied pixels.

Host resize reconfigures the surface only. Preserve the current zero-dimension
clamp to one; this is not a claim that a minimized window is visible. Resize
does not mutate logical texture descriptors or enlarge existing targets. A
caller requiring newly sized render targets creates new definitions/mappings
and retires old uses under the same ownership rules. Borrowed native window
and display handles must outlive their SGFX window context.

Surface acquisition/loss is a fallible presentation operation. There is no
automatic frame replay or common surface/device recovery guarantee. A failed
presentation does not undo previously accepted rendering or authorize reuse
of an externally leased image. Recover/reconfigure only through the backend's
documented boundary; otherwise rebuild. No new mandatory surface-status API
is required for 1.0.

Where an existing readback API promises synchronous completion, success makes
the requested destination pixels available to the CPU before returning. It
does not wait for unrelated queues or consumers, and an error need not leave
the destination untouched.

## 9. Runtime features and backend selection

The [inventory's feature recipes](1.0-api-scope.md#feature-and-backend-selection-contract)
describe the current build interfaces. Facade `std` and `legacy-scarlet-std`
are runtime-and-backend bundles enabling the existing `backend-*` feature names;
`scarlet-std` is a legacy alias and core `std` is an empty compatibility feature.
These recipes remain unchanged by this decision. A future change follows
section 2: update the consumers, build configurations and documentation in the
same compatible source set, without silently changing a recorded configuration.

Both normal Scarlet targets use Rust std. Legacy JSON targets use the separate
legacy recipe; enabling both runtimes is not a supported recipe. Backend-free
core/facade configurations do not imply that host WGPU itself is no_std.

The current backend strings and aliases, case-sensitive parsing,
environment-lookup feature boundary and explicit-selection errors remain as
documented in the inventory. `Auto`
permits initial backend selection, not silent fallback after failed execution.
`Instance::backend()` on Scarlet reports a compiled default until a device is
opened; `Device::backend()` identifies the selected device backend. `metal`
remains reserved/unavailable in 1.0; WGPU running on Metal is still `wgpu`.

## Pre-RC conformance work, in contract order

The architecture, coordinated Rust update policy and completion scope are
agreed. Remaining rendering and lifecycle proposals still need review.
Track the [asynchronous submission checkpoints](completion-contract.md#implementation-checkpoints)
alongside these conformance obligations:

1. Keep the frontend, IR, backend and codegen implementations consistent in
   the selected revision set. Record the meaning and supported subset of any
   changed operation and update affected Rust consumers together. A blanket
   enum migration or Rust API freeze is not an RC gate.
2. Audit backend lowering against section 4 and publish supported-subset tables.
   Cover coordinate/depth conventions, partial areas, optional depth, layout
   limits and rejection without raw-driver validation errors. Current WGPU
   rejection of depth-disabled pipelines in depth-attached passes must be
   classified as unsupported, not as invalid portable IR.
3. Verify native import/release/teardown against section 7, including partial
   failure and outstanding work. Audit SWS's independent lease transitions;
   success-path readback tests do not certify failure-safe buffer reuse.
4. Audit native/direct execution and resize/surface-loss paths against their
   ownership and execution rules. Include exposed dependency types when
   checking that the coordinated Rust source set builds; they do not create
   an independent application ABI.

Only after that work may conformance tests, hardware evidence and coordinated
release staging close their respective gates. This decision adds no version
bump or requirement to finish a Vulkan frontend. The newly agreed completion
API and asynchronous Scarlet path are required before claiming 1.0 readiness.
