# Rust integration inventory for SGFX 1.0

Status: inventory of the Rust interfaces in a coordinated driver/renderer build.
The packages are still 0.16.0. The [1.0 execution contract](1.0-contract.md)
records the approved coordinated Rust update policy and the remaining rendering
and lifecycle review targets. The agreed
[completion scope](completion-contract.md) includes actual asynchronous Scarlet
submission as well as portable completion tracking; this
inventory does not certify conformance. Read both with the
[execution contract](execution-contract.md) and Scarlet's coordinated release
scope. The [architecture](architecture.md) maps issue #1 to these existing
surfaces. They retain their Rust visibility but have no blanket 1.x source
freeze; affected consumers migrate and rebuild together.

## The implemented portable IR

The current IR describes drawing and transfer operations, not an arbitrary
shader or compute API:

- Two-dimensional `Bgra8Unorm`, `Rgba8Unorm`, `R8Unorm` and `Depth32Float`
  textures. Depth currently permits only `RENDER_ATTACHMENT` usage: it cannot
  be uploaded, copied, presented, or sampled through this IR.
- Nonempty byte buffers with vertex/index/copy usage, samplers, and owned
  render-pipeline descriptors. Resource definitions are append-only within
  bounded tables; defining a resource does not allocate GPU memory.
- One interleaved vertex buffer, `TriangleList`, 16/32-bit indices, and
  `Float32x2`, `Float32x3`, `Float32x4` or `Unorm8x4` attributes. Position is
  location 0; fragment descriptors define the color/texture-coordinate slots.
- `Solid`, `VertexColor`, `Texture` and `TextureVertexColor` fragment programs,
  with a transform/color uniform, sampler state, blend state, culling/winding,
  scissor, and optional depth comparison/write state.
- One color attachment and an optional same-sized `Depth32Float` attachment
  per pass. Load/store operations and nonempty rectangular render areas are
  explicit. A depth-enabled pipeline requires a matching depth attachment.
- Borrowed buffer/texture uploads, format-preserving texture copies, render
  passes and direct/indexed draws. The command stream preserves recording
  order. Core validation checks index-buffer byte ranges, not opaque uploaded
  index values or device-specific vertex-layout constraints.

IDs identify a resource definition in one originating table, not a bare numeric
slot or a GPU handle. Moving an owned table preserves its IDs; another table's
equal-sized resource is not interchangeable. Dropping an ID does not remove
the definition or free its slot. The table uses interior mutability and is
not a shared concurrent recording object. Backends own their physical caches.
This does not prevent rebinding a compatible imported physical image after
successful explicit release; the logical definition and table ID stay fixed.

There are no arbitrary shader modules, compute dispatch, multiple color
attachments, mip/array/3D texture descriptors, explicit barriers, or common
cross-queue synchronization operations today. Portable completion receipts
now exist outside the IR, with WGPU and native VirGL implementations. A618
asynchronous execution and hardware conformance remain 1.0 gates.
Completing those future extensions is not required to release the current
subset. Calling the IR portable does not mean every valid descriptor is
supported by every backend/device.

## Feature and backend selection contract

| Configuration | Current meaning |
| --- | --- |
| `sgfx` defaults, host | Rust std and the WGPU host facade; native backend dependencies are target-gated. |
| `sgfx` defaults, normal Scarlet target | Rust std, with the compiled VirGL and Adreno backends selected against the opened GPU. Both `riscv64gc-unknown-scarlet` and `aarch64-unknown-scarlet` are std userspace targets. |
| `sgfx`, `default-features = false`, no features | Backend-neutral IR/trait reexports and selection types, without a runtime or executor. Attempting to select an unavailable backend returns an error. |
| Host `sgfx`, no defaults, `backend-wgpu` | The WGPU facade is available, but SGFX's std environment-lookup feature is off. WGPU itself still requires host std; this is not a bare-metal WGPU backend. |
| `sgfx`, no defaults, `legacy-scarlet-std` | The older Scarlet userspace runtime and compiled native backends for the legacy JSON targets. `scarlet-std` is a retained compatibility alias. This is not the normal Scarlet configuration. |
| `sgfx-core`, with or without `std` | Always `no_std` plus `alloc`; its empty `std` feature remains a compatibility name. `sgfx-codegen-virgl` is also `no_std` plus `alloc`. |

Today both facade runtime bundles, `std` and `legacy-scarlet-std`, enable all
three `backend-*` feature names. Thus `--no-default-features --features std`
does **not** select a std-only facade with no backend. This is the current
composition, not a frozen 1.x recipe. Changes follow the approved coordinated
update policy and must include consumers and build configuration.
Native backend-only features are not substitutes for selecting the appropriate
native runtime bundle. Selecting both runtime bundles is not a supported
legacy configuration; use the normal std or legacy recipe, not `--all-features`
as a cross-target support claim.

`SGFX_BACKEND` accepts `auto`, `wgpu`, `metal`, `scarlet-virgl` and
`scarlet-adreno`; `virgl` and `adreno` remain aliases. Parsing is case-sensitive
and does not trim whitespace. Without a supported runtime lookup, the
environment preference is `Auto`. An explicit unavailable backend is an
error, not permission to silently choose another backend. `metal` is a
reserved, currently unavailable direct backend; WGPU using Metal is `wgpu`.

On Scarlet, `Instance::backend()` under `Auto` reports a compiled default,
not a device probe. Use the opened `Device::backend()` for the selected GPU.
The facade's Scarlet capability booleans and host `supports_depth()` are not
a portable, per-format/per-operation/device-limit capability query.

## Execution policy and remaining semantic review

The [execution contract](execution-contract.md) defines ordering, upload
ownership, queue acceptance, explicit errors and non-transactional failures.
The approved completion scope retains the old acceptance boundary while adding
tracked submission, owned receipts, observation and waiting. A possible partial
submission failure carries a receipt, rather than authorizing automatic replay.
No common per-format capability query or device-loss recovery API is required.
Backend-specific errors remain public, and raw WGPU errors may still be
observed asynchronously after acceptance. Unsupported valid operations must
be reported explicitly rather than leak as avoidable driver validation errors.

The draft imported-image contract proposes requiring successful explicit
release to retire both the native session mapping and that session's outstanding uses.
It is not an SWS frame-release acknowledgement. A by-value imported handle
transfers one owned reference to the backend; the producer's content lease is
separate and follows the matched SWS generation/epoch/serial lifecycle.
Release failure and `Drop` do not authorize buffer reuse. Native failure-path
conformance with this target still needs verification.

Git dependencies carrying SGFX types must resolve to one `sgfx-core` source.
The workspace's self-source override is only for local development with the
external Adreno backend. Consumers do not inherit or need it. The coordinated
release still needs its immutable Git-selector/lockfile rehearsal.

## Evidence and remaining review

The portable suite now has 35 default-configuration tests, including 13
GPU-independent recording tests and 3 new real-device WGPU rejection tests.
The rejection tests cover byte alignment and resource-size limits, checking
both the SGFX error and absence of raw WGPU validation errors. They do not
claim exhaustive validation of every device limit or fault path.

Both host compilers also test the facade with no defaults and with only
`backend-wgpu` (4 tests per configuration). CI checks the backend-neutral
facade on both normal Scarlet targets in addition to the existing std checks.
Legacy runtime coverage remains in Scarlet's integration tasks. Compiler
build directories remain separate; Scarlet Rust is the primary compiler.

Before RC1, settle the remaining semantic proposals and finish these conformance
items under the approved coordinated Rust update policy:

- Check that frontends, IR, backend lowerings and codegen agree on the selected
  operation meanings and supported subset. Migrate affected Rust consumers
  together when those interfaces change. No blanket enum migration is required.
- Complete rendering-semantics and backend-subset tests, including device
  vertex-layout limits/alignment and optional-depth combinations. WGPU
  currently requires pass/pipeline depth-state presence to agree and rejects
  partial rectangular depth clears; a `supports_depth()` boolean is not a
  promise that every depth combination works.
- Audit public native/direct-backend APIs and imported-image release on
  failure, surface resize/loss, and owner teardown. Do not infer failure
  recovery or leak freedom from the successful render/readback tests.
- Complete the matched SWS/native-runtime and A618 evidence, then record the
  exact supported subset/configuration and immutable candidate revision set.

This inventory records the approved internal Rust integration boundary. It
does not introduce release tags, package-version changes or API removals.
